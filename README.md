# MemLedger (`dsh-memledger`)

**[中文](README.md)** | **[English](README.en.md)**

> **空间有地图，时间有台账。**  
> 为 DeepSeek Harness (DSH) 量身打造的工程管控与智能记忆插件：改动前查重与倒车预警，改动后沉淀「为什么」，彻底根治 AI 编程中**做歪、全盘乱扫、做重复、以及把已修好的功能无情改回**的核心痛点。

---

## 🎯 为什么需要 MemLedger？

在长线项目迭代中，上下文能力一般的 AI（乃至顶尖模型）最昂贵的损耗往往不是“代码写不出来”，而是：
1. **宏观迷航（空间失焦）**：每次接到任务漫无目的地全盘扫描项目（大量 `glob`/`grep`），注意力被无关代码稀释，找错入口，把功能做歪；
2. **重蹈覆辙（时间失忆）**：AI 缺乏跨会话的负向记忆。三个月前被证明会导致死锁并废弃的方案，AI 换个会话又热情洋溢地重写一遍，把原本稳定的修复改回老坑。

MemLedger 遵循**「空间有地图，时间有台账」**的双闭环原则，将两套机制合为一体：
* **空间地图（Repo Map）**：将全项目代码提炼为不到 2000 Tokens 的高密度骨架图，AI 不读源码即可秒懂全局架构；
* **时间台账（Change Ledger）**：以物理代码锚点（`文件::符号`）为索引，强制记录「改动为什么」与「否决为什么」，提供实时的倒车与重复修复拦截。

## 🖼️ 界面特性：会话顶部并列看板

插件在 DSH 客户端（桌面端与 Web）的会话顶部注册了原生视图（`conversation.view`），与**【对话】、【轨迹】、【版本】**无缝并列：

```
┌──────────┬──────────┬──────────┬────────────────────────┐
│  对话    │  轨迹    │  版本    │  台账与地图 (MemLedger) │
└──────────┴──────────┴──────────┴────────────────────────┘
```

点击 **[台账与地图]** 即可唤起三页驾驶舱：
* **📊 效能**：工具调用、决策沉淀、风险拦截的实时仪表盘；
* **🗺 骨架与台账**：左栏空间拓扑（文件/行数/导出签名），右栏时间台账（决策卡片、检索、未决过滤）；
* **🧪 契约跑分**：每个程序的契约卡——最近分数、趋势、用例通过情况、已落地却无用例的欠账；
* **极高韧性**：底层采用可选路由与前端沙箱隔离，网络异常时优雅提示，**绝无任何白屏风险**。

## 🤖 八大核心 Agent 工具

插件向 DSH 注册了八个轻量原子工具，嵌在 AI 的标准思考循环中：

| 工具 | 触发时机 | 核心回答与能力 |
|---|---|---|
| **`ledger_map`** | **探索项目 / 改代码前** | 获取或刷新代码骨架地图，无需盲目全盘扫描即可获取导出符号与 API 签名 |
| **`ledger_check`** | **动手改代码前一秒** | 检查目标文件或符号做过没有？当初为什么改？修复是否被改没了？命中契约时附分数 |
| **`ledger_requirement`** | **提出需求 / 开工建目录时** | 把用户诉求规范化成 `docs/需求/RQ-YYYYMMDD-NN.md`：原文逐字保留、范围 / 验收口径 / 明确不做的事 |
| **`ledger_add`** | **功能落地 / 方案放弃后** | 沉淀决策依据（13 字段），特别是将“走不通而放弃”的方案记入负向记忆；可挂 `requirement` 成为子项 |
| **`ledger_suite`** | **改完代码 / 收口前** | 程序的契约套件：登记可执行用例、跑分、按锚点选测；分数进历史，断言被手改会报漂移 |
| **`ledger_search`** | 遇到疑问想查历史时 | 按关键词、错误特征、代码锚点检索，未决/否决条目自动置顶 |
| **`ledger_verify`** | 交付前整体体检时 | 扫描已落地锚点是否存活；报「引用了不存在的需求」「套件漂移 / 用例锚点已死 / 零用例欠账」 |
| **`ledger_bootstrap`**| 新项目初次接入时 | 从 Git 提交历史或已有文档全自动提炼生成首版台账 |

### 需求层：给台账一个目录

台账条目回答「这次改了什么、为什么」，但回答不了「这几个改动属于同一条诉求」。需求层补的就是这一层：

```
docs/需求/RQ-20261113-01.md      ← 一条完整诉求（可编辑的状态文档）
  ├─ CL-20261113-11  工具改用会话 cwd 解析根
  ├─ CL-20261113-12  零数据卡片常显
  └─ CL-20261113-13  样式整修（待真机截图）
```

- **需求是活文档，台账是证据链**：需求可以勾选、改状态、补验收；台账仍然只追加。
- **ID 是连接键**：条目写 `- **需求**：RQ-…`，需求文件列子项。跨仓需求因此不需要搬迁历史——两个仓各自的台账都能用同一个 ID 拼回一条时间线。
- **重复判定分层**：同一需求内的多轮改动算「后续轮次」，放行；跨需求的同锚点改动仍然挡回。
- **目录自动生成**：`变更台账.md` 的 `1.3 按需求分组` 会自动列出需求链接、子项数与未决数。
- **跟 git 对齐**：需求 ID 写进分支名/提交尾注（`需求: RQ-…`），条目里记真实 hash，需求文件的「代码与提交」段落沉淀分支与提交范围。

不是每条改动都值得建需求。建议阈值：**子项 ≥ 2 条、跨两个仓、或有需要事后验收的口径**。单条小修直接 `ledger_add` 即可。

### 契约层：把「验收」从散文变成可执行证据

台账回答「为什么改」，契约套件回答「改完还是不是对的」。三个文件、三件事：

| 文件 | 作用 |
|---|---|
| `docs/验收/<程序>.json` | 契约：用例 = 命令 + 退出码/stdout 断言（声明式、极小、哈希冻结） |
| `docs/.memledger-runs.jsonl` | 跑分流水：每次结果一行，构成分数趋势（append-only） |
| `docs/程序/<程序>.md` | 程序卡：契约清单 + 跑分 + 台账条目 + 欠账（自动生成，勿手改） |

- **按锚点选测**：用例用 `covers: ["lib/x.js::fn"]` 登记；改了哪个锚点就只跑覆盖它的那几条，不传 `paths` 才跑全套。
- **分数**：加权通过率 `Σ(权重×通过)/Σ权重`。倒车用例权重给 5，需求验收口径 3。**全套分与选测分分开记**——选测只证明这次改动没踩线，不代表程序整体健康。
- **接线**：`ledger_check` 命中受保护路径时多一行 `🧪 契约 C-001/C-003（上次 100 分）`；`ledger_add` 在「已落地」时把分数自动写进 `验收` 字段；`ledger_verify` 报三种腐坏：断言被手改（哈希漂移）、用例锚点已死、已落地但零用例（欠账）。
- **防自证通过**：不引入测试框架；`update` 改断言必须给 `reason` 并补一条「类型=口径」的台账；用例数/权重变化写在程序卡里，缩范围换来的高分一眼可见；新用例建议先看到它红一次（`seenFail`）。
- **界面只读**：GUI 展示程序卡、用例与分数趋势，**不提供执行入口**——127.0.0.1 上无鉴权的 POST 执行不是特性，是洞。跑分由 agent 触发。

### `ledger_check` 的智能判定矩阵

| 判定标识 | 严重度 | 实际含义 | AI 与人类该采取的动作 |
|---|---|---|---|
| `rollback-risk` | 🔴 极高风险 | 历史上的关键修复代码已经在当前文件中丢失！ | ⚠️ 立即停手，极大概率正在重踩同一个历史大坑 |
| `repeated-repair` | 🟡 警告 | 同一个函数或符号已经历经多次重复修复 | ⚠️ 停手先读历次「为什么」，切勿做盲目打补丁 |
| `shelved` | ⚠️ 警示 | 该方案曾经尝试过，但因故被决策**搁置/否决** | ⚠️ 先核对台账中的「重启条件」是否满足，严禁重走老路 |
| `already-done` | 🟢 安全 | 该功能已落地且物理锚点存活 | 该逻辑已有成熟实现，无需重复造轮子 |
| `unrecorded` | ⚪ 全新 | 无任何历史记录 | 确认属于新场景，放行改动，做完调用 `ledger_add` |
| `foreign-anchor` | ⚪ 跨仓 | 锚点指向外部关联仓库 | 需前往目标仓库核对 |

## 📐 13 项台账标准字段规范

`docs/变更台账.md` 采用规范严苛的 append-only Markdown 结构：

| 字段 | 含义说明 | 真实示例 |
|---|---|---|
| **日期** | 改动实际发生日期 | `2026-10-28` |
| **类型** | 修复 / 新功能 / 重构 / 口径 / 部署 / 决策 / 埋点 / 演练 / 文档 | `重构` |
| **状态** | 已落地 / 进行中 / 待验证 / 搁置 / 未做 / 已回退 / 已废弃 | `已落地` |
| **仓** | 涉及仓库名称 | `dsh-memledger` |
| **需求** | 可选。所属需求 ID，指向 `docs/需求/RQ-….md` | `RQ-20261113-01` |
| **背景** | 现状是什么，为什么出现这个问题 | `老版本看板强依赖 webServer，导致无服务环境加载报错` |
| **改动** | 实际上做了什么技术变更 | `移除强依赖，改用可选路由注入与客户端异常沙箱` |
| **为什么** | 核心决策依据（**非落地状态必填**） | `保证工具纯度第一，界面只作为非阻断的可选呈现` |
| **取舍** | 付出的代价，或搁置条目的**重启条件** | `代价：需要额外维护双层容错；换来：零白屏故障面` |
| **锚点** | 代码的物理定位（`文件::符号`） | `lib/index.js::apply` |
| **commit** | Git Commit Hash | `4541e1e` |
| **验收** | 验证命令或测试用例 | `契约 C-001/C-003 · 7/7 通过 · 100 分` |
| **关键词** | 检索标签 | `看板, 容错, 优雅降级, client` |

## 🚀 全局自动注入与零配置体验

插件激活时，会自动在用户的全局规则 `~/.dsh/AGENTS.md` 中安全挂载如下规范（带有 `<!-- BEGIN DSH-MEMLEDGER-RULES -->` 幂等签名，不侵入用户原有的自定义规则）：

1. **开工前**：
   - 需求跨多条改动 / 跨仓 / 有验收口径时，先用 `ledger_requirement` 建需求；
   - 必须先看 `docs/项目结构.md`（或调用 `ledger_map`）定位文件边界；
   - 必须调用 `ledger_check` 核对历史，确认无否决与倒车风险；
2. **完工后**：
   - 必须调用 `ledger_add` 将决策因果入册（有需求就传 `requirement`）；
   - 必须调用 `ledger_map` 刷新代码骨架地图。

用户在 DSH 中打开任何新项目，均可享受全自动护航。

## 📦 打包与发布到插件市场 (dshmarket)

### 1. 本地测试与体检
```bash
# 执行完整测试套件（覆盖工具契约、风险判定、规则注入、客户端插槽）
npm test
```

### 2. 发布准备
确保 `package.json` 中的版本号、描述与关键字就绪后：
```bash
# 打包为 tgz 压缩包
pnpm pack
```

### 3. 安装到 DSH
在你的 DSH 桌面主配置（`~/.dsh/profiles/desktop/package.json`）中添加依赖：
```json
{
  "dependencies": {
    "dsh-memledger": "^0.1.0"
  },
  "dsh": {
    "profile": {
      "bundles": [
        "dsh-memledger"
      ]
    }
  }
}
```
并在 `~/.dsh/profiles/desktop/cordis.patch.yml` 中挂载：
```yaml
- id: dsh-memledger
  name: dsh-memledger
```
重启 DSH 客户端即可畅享完整的“空间地图 + 时间台账”双闭环！

### 💡 针对 DeepSeek 模型环境的推荐配置（防流式 JSON 抖动）

在部分以 DeepSeek 为底模的运行环境中，大模型在单轮生成较长工具调用参数时可能偶发流式 JSON 格式抖动。建议在 DSH 配置中将 `MALFORMED_RESPONSE` 纳入重试白名单，避免偶发抖动导致整轮会话中断：

```yaml
# 在对应 provider 补丁中增加：
- patch:
    id: deepseek
    config:
      retryPolicy:
        retryableCodes:
          - EMPTY_RESPONSE
          - RATE_LIMIT
          - SERVER
          - TIMEOUT
          - TRANSPORT
          - MALFORMED_RESPONSE
```
